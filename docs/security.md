# Безопасность репозитория и ключей Firebase

## Коротко

- Репозиторий **публичный** (создан 26.09.2026). Всё, что попало в коммиты,
  считается опубликованным — в том числе история.
- «Спрятать пароль в открытом коде» нельзя: любой может прочитать исходник,
  декодировать обфускацию и собрать клиент. Пароль нужно **убрать из кода**,
  а не замаскировать.
- Секретов в игре больше не должно быть вовсе. Пароль проверяет Firebase Auth,
  доступ к данным ограничивают правила базы, а не константа в клиенте.

## Что НЕ является секретом

| Значение | Где | Почему это нормально |
|---|---|---|
| `AIza…` (Web API key) | `src/engine/network.h`, `index.html` | Это идентификатор проекта Firebase, а не ключ доступа. Так задумано: он есть в любом веб-клиенте. Доступ режут правила базы и Auth. |
| URL базы `…firebaseio.com` | `src/engine/network.h` | Публичный адрес проекта. |
| Имена комнат (`main`, …) | `NET_DEFAULT_ROOM` | Не секрет. |

Если правила базы настроены верно, публикация этих значений ничего не даёт
атакующему.

## Что утекло (до правки)

### 1. Пароли администраторов — критично

`src/game/state/create/core/config_part2.inc` — две константы с паролями
администраторов (`ADMIN_PASS` и `ADMIN2_PASS`); конкретные значения остались
в истории репозитория, поэтому здесь они не повторяются.

Пароль аккаунта в Firebase Auth — это `<введённый пароль> + <хвост пароля>`
(см. ниже). Значит, из репозитория напрямую собирался пароль от админского
аккаунта `Dimasi4ek229@cb4.game`, а правила базы дают этому аккаунту полную
запись: банны, баннер, ивенты, подарки, прогресс любого игрока.

**Исправлено в коде:** константы удалены; право администратора теперь
определяется аккаунтом (успешный вход в него), а не сравнением пароля в
клиенте. **Но сам пароль аккаунта всё ещё старый — его нужно сменить.**

### 2. Поле `w` («пароль на запись») — не секрет по устройству

- Лежит открытым текстом в `firebase.rules.json` (11 раз).
- Клиент дописывает `"w": "<секрет>"` в **каждое** тело записи — значит, он
  сохраняется в каждом профиле `users/<ник>/w`.
- Профили читает любой вошедший игрок (`".read": "auth != null && …@cb4.game"`).

То есть значение доступно и из репозитория, и из базы любому игроку. XOR 0x5А
в `src/engine/network.h` ничего не защищает: функция декодирования лежит рядом.
Схема не даёт защиты от того, кто уже залогинен, — а до записи без логина
правила и так не допускают.

**Вывод:** это надо не перепрятывать, а убрать. Порядок — в разделе «План».

### 3. Хвост пароля (pepper)

32 символа в `src/engine/network.h` (тоже XOR). Клиент дописывает его к
паролю при входе и регистрации. Он есть в каждом APK и в исходниках, поэтому
«секретом» не является; польза — только против совсем простого перебора
паролей. В связке с `ADMIN_PASS` он и сделал утечку критичной.

## Что уже сделано

- Пароли администраторов удалены из кода и из тестового харнесса.

  `net_login_status() == 2 && admin_slot(net_login_nick()) != 0`.
  Подделать ник нельзя — это e-mail `<ник>@cb4.game`, занятый в Firebase Auth.
- Добавлен сторож `tools/check_secrets.py`, он же шаг CI: падает, если в
  репозитории снова появятся объявления паролей админов со строкой в
  кавычках, приватные ключи, `.env`,
  `.pem`/`.p12`/`.jks`/`google-services.json` или значения из `.secrets-deny`.
- В `.gitignore` добавлены локальные файлы секретов.

## Что нужно сделать вручную (порядок важен)

1. **Сменить пароли админских аккаунтов** `Dimasi4ek229@cb4.game` и
   `qwertyuiopaj1234@cb4.game` в Firebase Console → Authentication.
   Помните про хвост: пароль в базе = `<то, что вводится в игре>` + хвост.
   Проще всего сменить его через саму игру (или функцию сброса), чтобы хвост
   подставился автоматически; при смене из консоли задавайте сразу
   `<новый пароль><хвост>`. Пароль должен быть случайным, 20+ символов, и
   храниться в менеджере паролей, а не в репозитории.
2. Проверить, что старый пароль больше не пускает, а новый — пускает.
3. Записать утёкшие значения в локальный `.secrets-deny` (по одному в строке),
   чтобы сторож ловил их возврат. В git этот файл не попадает; для CI те же
   строки можно положить в GitHub Actions secret `CB4_SECRET_DENY`.

## План: убрать общие секреты совсем

1. **Убрать `w`.** В правилах заменить проверку
   `newData.child('w').val() == '<секрет>'` на проверку личности
   (`auth.token.email == $nick + '@cb4.game'`), которая там уже есть.
   Валидацию полей (границы кубков, счётчики подарков и т.п.) не трогать.
   Старые клиенты продолжают слать `w` — правило должно разрешать строку,
   чтобы обновление прошло безболезненно. После выкладки правил секрет
   перестаёт что-либо защищать и его можно удалить из клиента.
2. **Убрать хвост пароля.** Перейти на пароль как есть. В коде уже есть
   механизм переезда: `fb_sign_in_legacy()` пускает старый аккаунт по
   `|cb4v1` один раз и сразу переписывает пароль (`fb_update_password`).
   Нужен такой же одноразовый проход для текущего хвоста, после переезда
   всех активных аккаунтов хвост удаляется.
3. **Админ-роль на сервере.** Право на банны/ивенты должно проверяться
   правилами (e-mail админа или custom claim), а не клиентским флагом.
   Сейчас правила уже ограничивают запись админскими e-mail — клиентская
   проверка нужна только чтобы показать панель.
4. **Секреты сборки.** Если когда-нибудь понадобится настоящий секрет в
   клиенте (например, ключ стороннего API), он передаётся в сборку из
   GitHub Actions secrets и в репозитории остаётся только заглушка.

## Секреты в GitHub Actions

GitHub Actions secrets нужны только самому CI, и **не решают проблему секрета в
клиенте**: всё, что вкомпилировано в APK или `.exe`, читается любым игроком.
Если значение нужно игре на устройстве — это не секрет, а публичная константа,
и защищать надо правила базы, а не строку в коде.

Сейчас секретов не требуется: сборка APK, `.exe` и все тесты идут с нулём
настроенных секретов, это подтверждает зелёный CI.

| Секрет | Нужен? | Зачем |
|---|---|---|
| `CB4_SECRET_DENY` | по желанию | Список уже утёкших значений для `tools/check_secrets.py` (в коде — `.secrets-deny`, в CI — этот секрет). |
| Release-keystore | пока нет | В репозитории лежит только `debug.keystore` — он публичен по своей природе. Для публикации в Google Play понадобится ключ релиза: `KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD`. |
| `FIREBASE_TOKEN` | пока нет | Если захочется выкладывать `firebase.rules.json` в базу прямо из CI. Пока правила публикуются вручную из консоли. |
| Service account Firebase | нет | Не нужен: клиент ходит в базу от аккаунта игрока. |

Никогда не кладём в секреты CI и не пишем в клиент:

- пароль администратора — его проверяет Firebase Auth, в коде его нет;
- `w` и хвост пароля — они и так в каждом теле записи и в каждом APK;
- Web API key — это публичный идентификатор проекта, а не ключ доступа.

### Безопасность самих секретов

- Workflow запускается только по `push` и `workflow_dispatch` (не по
  `pull_request`), поэтому посторонний форк не получит доступа к секретам.
- `permissions: contents: read` — токен workflow ничего не может записать в
  репозиторий.
- GitHub маскирует значения в логах, но полагаться только на это нельзя:
  не печатать секреты через `echo`, `set -x`, `env` и не передавать их в
  сторонние сервисы.

## Правила гигиены

- Пароли — только в Firebase Auth. В коде, тестах, документации и скриншотах
  их быть не должно.
- Токены и ключи — в GitHub Actions secrets, не в файлах репозитория.
- `python3 tools/check_secrets.py` — локально перед коммитом; в CI шаг уже есть.
- Помнить: APK и `.exe` содержат всё, что вкомпилировано. Любой «секрет» в
  клиенте считается публичным.
